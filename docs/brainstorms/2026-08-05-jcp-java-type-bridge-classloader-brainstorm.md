# Brainstorm: JCP ↔ Java Type Bridge Across Classloader & Context Boundaries

**Date:** 2026-08-05
**Status:** Ready for planning
**Related issue:** #50

## What We're Building

A systematic **JCP ↔ Java type bridge** that fixes real defects hit when calling a
user-provided JAR in compile mode, and hardens the boundary for the growing set of
STD APIs (`Strings`, `Math`, `Stdio`, and third-party modules).

This is a **real bug**, not a speculative hardening pass — a user JAR failed in
compile mode with a mix of classloader errors and bad round-trip values, and the
root cause has **not yet been isolated** between two candidate mechanisms.

## Why

As STD APIs and third-party modules multiply, the JCP↔Java boundary is held together
by ad-hoc unwrapping and JCP-inferred descriptors. A code audit found **five concrete
defects** on this boundary, several of which can independently explain the failure the
user hit. Without a systematic bridge, every new module risks re-triggering them.

### The five defects found in the audit

| # | Location | Defect | Mode |
|---|----------|--------|------|
| D1 | `FunCallCompiler.compileModuleFunctionCall` (`Class.forName`, lines 266/332/347) | Loads the target Java class with **no explicit classloader** → resolves against JCP's own loader, not the user-JAR loader | compile |
| D2 | `MultiClassLoader` (line 15) | Parent hard-wired to `MultiClassLoader.class.getClassLoader()`, **not** the thread context classloader → generated bytecode can't see host/plugin/user classes at runtime | compile |
| D3 | `FunCallCompiler.compileModuleFunctionCall` (lines 291–296) | `INVOKESTATIC` descriptor built from **JCP-inferred arg types**, not the actual Java method's parameter types → `ANY`→`Ljava/lang/Object;` produces a descriptor matching no real method (`NoSuchMethodError` / VerifyError) | compile |
| D4 | `FunCallCompiler.compileModuleFunctionCall` (lines 285–289) | **No boxing** for static module calls (constructors box via `boxPrimitive`, static calls don't) → pushes `int` where descriptor says `Object` → verifier error | compile |
| D5 | `CompileModeClassConverter.mapJavaTypeToDataType` (lines 112–159) | `long`/`float`/`char`/`byte`/`short` and all class types silently collapse to `ANY` → wrong descriptor recorded | compile |
| D6 | `ClassConverter` (line 235) | Constructor registration references undeclared `arguments` (param is `parameters`) → broken code path | eval |

### How they map to the reported symptoms

- **ClassNotFoundException / ClassCastException with a user JAR** → D1 and/or D2
  (loader visibility). The user JAR was on the compile-time classpath but its runtime
  loader relationship to `MultiClassLoader` is unknown.
- **Bad round-trip value** → D3/D4 (descriptor & boxing mismatch on the `ANY` boundary).

The user was calling the JAR via **both paths**: registered static module functions
(`Type.method(...)` → `compileModuleFunctionCall`) **and** `new Type()` /
instance methods (`ExternalClassType` / `MethodCallCompiler`).

## Scope

### Deliverables (sequenced PRs)

The user chose to **split into sequenced PRs**. Because the root cause is not yet
isolated, PR 1 is a reproduction harness that decides what the remaining PRs must fix.

**PR 1 — Reproduce & isolate the user-JAR failure**
- A test fixture that mimics a user JAR loaded via a **child/URL classloader**
  (distinct from JCP's loader), exercised through **both** call paths (static
  module function + constructor/instance method).
- Assert which of D1–D5 actually fires; capture the exact exception & stack.
- Outcome: a red test that pins the real bug, plus a decision on whether the primary
  fix is loader-visibility (D1/D2) or descriptor/boxing (D3/D4/D5) — likely both.

**PR 2 — Descriptor & boxing correctness at the Java call boundary (D3, D4, D5)**
- Build the `INVOKESTATIC` descriptor from the **resolved Java method's actual
  parameter/return types**, not JCP-inferred arg types.
- Emit boxing/unboxing/widening at static module call sites, mirroring the existing
  constructor path (`boxPrimitive` + `TypePromotion`).
- Extend `mapJavaTypeToDataType` to cover `long`, `float`, `char`, `byte`, `short`
  (+ boxed/array forms) — or explicitly document what stays `ANY` and why.

**PR 3 — Classloader isolation (D1, D2)**
- Pass an explicit classloader to `Class.forName` in `FunCallCompiler`.
- Make `MultiClassLoader`'s parent configurable (default to a sensible chain that
  includes the context/registered loader); provide a `registerClassLoader` hook for
  dynamic/user JARs.
- Document the classloader contract in `JcpCompiler` Javadoc.

**PR 4 — Eval-mode marshaling cleanup (D6 + systematization)**
- Fix the broken constructor registration (D6).
- Replace ad-hoc `Data.get()` unwrapping with a systematic marshal/unmarshal helper;
  ensure `STRING`↔`java.lang.String` round-trips through a single bridge.

### Out of Scope
- Redesigning `SystemDataType` or the type hierarchy.
- Full OSGi/servlet-container support (only the general context-classloader hook).
- New STD API surface (this is a boundary fix, not new functions).

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Trigger | Real bug (user JAR, compile mode) | Fix must be anchored in a reproduction, not speculation |
| Root cause isolated? | No — PR 1 isolates it first | Both loader-visibility and descriptor/boxing are plausible; test decides |
| Landing size | Split into sequenced PRs | Smaller reviews, incremental coverage; user's explicit preference |
| Sequence anchor | Reproduction harness leads | Both call paths + unknown root cause demand evidence before fixes |
| Descriptor source | Actual Java method signature | Current use of JCP-inferred types is the descriptor-mismatch root (D3) |

## Open Questions

1. **Is PR 3 needed, or does PR 2 alone fix the user's case?** PR 1's isolation result
   decides this. If the user JAR was on the same loader, D3/D4 alone may suffice.
2. **`MultiClassLoader` parent policy:** context classloader by default, or an explicit
   registration API only? Changing the default parent risks behavior changes for
   existing embedders.
3. **`compileAndLoadWithReturn` uses a separate private `ByteArrayClassLoader`** (not
   `MultiClassLoader`) — does it need the same loader fix, or is it out of the bug path?
4. **`ANY` fallthrough policy** in `mapJavaTypeToDataType`: enumerate every primitive,
   or keep `ANY` as a documented catch-all with explicit boxing at the call site?
5. Should the eval-mode marshal helper (PR 4) and compile-mode descriptor logic (PR 2)
   share a single **canonical mapping table** to prevent the two modes from drifting?
